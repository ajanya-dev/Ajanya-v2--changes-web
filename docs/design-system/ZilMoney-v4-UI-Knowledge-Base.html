The Zil Money v4 UI Rebrand and Consistency Pass

A plain-language, phase-by-phase guide to the colour theme, the shared components, and how every screen stays consistent
Product
Zil Money web app (v4)
Workstream
design/zilmoney-rebrand
Audience
Design, Dev, QA, PM
Status
In design review

Overview

The v4 UI rebrand and consistency programme re-skins the Zil Money web app to the Zil Money brand and gives it one colour system, one sizing standard, one button system and one set of component states, applied the same way on every screen and meeting WCAG 2.2 AA in both themes. It ran on a design branch in seven stages: brand tokens and baseline, palette exploration, screen-by-screen UX passes, accessibility compliance, a consistency pass, a polish pass on the Add Payee modal and Send Payment, and a pass that makes every refused Confirm land on the field that is wrong.

Before the programme, the app carried the Online Check Writer look: legacy blues and a neon green, a mix of fonts, text below 12px, placeholder-only fields, 2.5:1 greys, undersized inputs, and colours typed by hand inside hundreds of components. Dropdowns came in several heights and radii, dark mode turned brand cards into glowing blocks, and busy screens such as Send Payment and the bank account pages carried badges and labels that repeated what the user already knew.

The journey, in plain terms:

  • Stage 1: the brand becomes tokens. Inter font, 8px radius, a contrast-verified text scale, 44/40/32px sizing tiers, and a scripted sweep that retires legacy hex values from 388 files.
  • Stage 2: the primary colour is explored on real screens. Cerulean, a deep teal, then Slate, then the navy #004a7c, with indigo and calm-teal comparison builds kept side by side.
  • Stage 3: screen passes. Send Payment, the header launcher, bank accounts, modals, section hub pages and the dashboard are decluttered and compacted, and the rules that came out of review are written down.
  • Stage 4: WCAG 2.2 AA. Tokens are fixed first, then components are swept for colour-only status, faint financial copy and unnamed icon buttons. A contrast script guards the result. The bank account card is rebuilt and compliance notices get a calm tone.
  • Stage 5: consistency. Dropdown rows, add-new tiles, banners, dividers, modal surfaces and dark-mode brand cards are unified, two long modals are simplified, and the reference, change log and this knowledge base are produced.
  • Stage 6: polish. The field border is lightened by decision, dark-mode text is softened, Send Payment gets two field heights and a guided prompt for missing payee details, and the Add Payee modal gets its final entity card, real send-link channel choices and 40px controls throughout. Hand-off files for the Add Payee and Add Customer modal states are produced.
  • Stage 7: landing. A review of the International rail finds four cases where a refused Confirm left the user with a dialog and no way to the field. All four are closed, and the screen-order rule now applies to every rail: the page lands on the top-most problem.

How we talk about it (guardrails)

  • This is a design-branch pass. Nothing here is live until the dev team merges it through the normal pipeline.
  • "Consistent" means the same token and the same recipe, not merely "looks similar".
  • The accessibility bar is a hard rule. A softer look never buys its way past a contrast failure. The one exception, the field border, was a named decision and is recorded with its figures.
  • Open items are listed honestly. Anything not fixed is named, with the reason.
01 | Knowledge

Knowledge

The master brief. Read this once and you understand everything that changed across the programme, and why.

The programme in full

The work ran in seven stages. Each stage built on the one before, and the rules that came out of review in one stage became the standard for the next.

Stage 1. Brand tokens and the UX baseline

The whole app was re-skinned to the Zil Money brand at the token level so every white-label build changed at once. Inter became the only typeface, the corner radius became 8px, and the text scale was rebuilt so that body, label, helper and placeholder text all clear 4.5:1 on white. A sizing standard was set from live competitor measurement of nine products: 44px for form fields and buttons, 40px for dense toolbars and filters, 32px inside table cells, with labels always visible at 14px medium, a 2px brand focus ring, and a 12px floor for all text. White-on-brand button text and AA placeholders were set in the shared input and button components. A scripted sweep then replaced legacy brand hex values, low-contrast greys and sub-12px text across 388 files, and a second sweep moved the legacy font variables to Inter in 70 files and put the Slate hero on the v4 login page. On Send Payment the bank account dropdown was decluttered: status pills became a verified icon and an amber Verify link, ACH moved into the detail line, the star shows only for the default or on hover, add-account became a one-line footer, and the account number was masked in the trigger. An attempt to render the page at 100% instead of its 0.85 zoom was reverted the same evening because the result felt bulky; the rule that came out of it is to declutter before enlarging. The design spec for the rebrand lives in the repo under docs/superpowers/specs.

Stage 2. Choosing the primary colour

The brand guide's Cerulean was tried first. A deep teal #145e68 from the colour recommendation was previewed on the sidebar, header, dashboard and Send Payment in light mode. Slate #415a80 was then adopted app-wide for buttons, links, focus and selection (white text 7.0:1; dark fill #4f6b96), with the Cerulean literals swept by script. The main copy then moved to the navy #004a7c with a light-blue page, and two comparison builds were created as git worktrees that share every layout change but keep a different palette: the earlier indigo #20319d on a pink-tinted page, and a calm teal #0f766e on warm off-white, inspired by how competitors sit one restrained accent on a neutral canvas. A sync script keeps all three identical apart from colour; every later change was applied to all three.

Stage 3. Screen passes

  • Header. A "+" quick-actions launcher at the start of the top bar, with favourites inside its panel and pinned favourite chips right after it. The gold favourite star colour became a token used by every star. "Pin to header" became "Pin to the top bar (next to +)" with an explainer line, and per-tile descriptions were rewritten in plain English as tooltips that search also matches. A standalone gold Favourites button was tried next to "+" and removed on review so the header keeps a single launcher.
  • Sidebar. Solid primary fill restored on the selected item.
  • Bank accounts. The stat boxes and full-width buttons of "All Bank Accounts" became one compact 64px summary strip so the table sits higher; the Transactions heading moved into the table toolbar (a new left-side toolbar slot on the shared data table) with a tighter section gap; the Edit Bank Account modal was regrouped into sections; the detail panel gained Account and Info tabs.
  • Send Payment. First-view compaction, one-line account rows, taller dropdown panels, a compact bank verification modal (icon-and-text intro row, 24px padding, one-line hint instead of the boxed Recommended panel, same trim on its success, error, pending and empty states), and the rule that a verified account shows a tick and a short "ACH" chip, never the word "Verified".
  • Modals app-wide. A compact dialog rhythm rule in the shared modal stylesheet and unified labels; payee and card modals brought onto the shared recipe; softer field strokes.
  • Section hub pages and dashboard. Section-page cards and banner rebalanced, the CTA banner moved onto the primary colour, dashboard wallet and upcoming-payment cards, and a light-blue page background throughout.
  • Verification Center. Re-laid on the shared cards with the current step in focus.

Stage 4. WCAG 2.2 AA and the bank account card

A compliance requirement made AA the app-wide bar. The audit measured 18 of 26 token pairs passing in light mode and 19 of 26 in dark. The fix went token-first: success green, warning amber and error red were darkened in light mode and lightened in dark, the error and sky badge text tokens were corrected, the favourite star darkened to #b98900, and the field border moved from a 1.5:1 grey to #7c8fa3 at 3.3:1. Those changes repaired roughly 1,300 usages at once. A component sweep then followed: brand text on dark surfaces switched to the bold token, green and red fills kept AA-safe shades under white text, status dots gained words and accessible names, about 260 icon-only buttons gained accessible names from their tooltips, primary buttons lost a teal label override so their white text shows, faint fee, warning and consent copy was raised to body weight, and every V2 control gained a visible keyboard focus ring. A Node script, tools/contrast-check.mjs, now checks every audited pair and fails on any regression. The spec and task plan live in the repo under docs/superpowers.

In the same stage the bank account detail card was rebuilt: the Info tab was merged into Account, balance and nickname became labelled grid items, the second and third information tiers became one aligned definition grid, the top-right button cluster was dropped in favour of a single pencil beside the name, account and routing numbers gained copy buttons with a brief tick, and the holder address renders on one line without stray commas. The Verification Center then gained an action-required panel for compliance cases (enhanced due diligence, re-verification, missing details) built from the same signals as the header badges. On review the red "Action needed" treatment was rejected as too strong for optional requests, so cases carry a severity: re-verification and missing-details notices are neutral and never red, only enhanced due diligence (which has a deadline) uses amber and reopens the business step, and the success family moved to emerald across the app.

Stage 5. Consistency

With the palette and the bar settled, this stage made every screen use the same recipe. Hand-typed indigo on the Bulk Payment Center became white tints and tokens and its "Coming Soon" badge a translucent white pill; the brand surfaces gained a dark-mode navy; feature icon tiles lost the slate accent; the CTA banner button became the teal fill; the Accounts page wallet intro became a shared, compacted component (and was removed from the dashboard on request); the Instant Demo, Add Category and Add payee modals were simplified; the wallet list matched the bank and card lists; the Send Payment dropdowns were unified in row, mask and add-new tile; a missing hover token was defined; and a read-only audit of buttons, dropdowns, modals, tables and states produced a fixed list and an open list. A lighter field border was tried and reverted the same day because it failed the 3:1 check. The UI reference (with ten live style samples), the change log and this knowledge base were written.

Stage 6. Polish on Send Payment and the Add Payee modal

  • Field border, by decision. The light field border moved from #7c8fa3 to #d1d5db, one shade above the staging grey, after #8395a8 and #8a9bad read too heavy and #e5e7eb a touch too faint. It measures 1.47:1 on white, so the 3:1 boundary rule is knowingly not met for field borders; the contrast script records it as a documented exception. Only the colour changed; the dark theme is untouched.
  • Dark mode text. Main text softened from #f8fafc to #e2e8f0 because bold wallet and account names glared; still 11.9:1 on the card.
  • Send Payment heights. The four main dropdowns are 44px (from 49px); everything under Additional details is 40px, including its dropdowns, the text inputs on every rail, the receive side, the page modals and the Memo minimum.
  • Missing payee details. Pressing Confirm with the payee's address, email or company missing opens a calm info prompt that names every gap ("Payee details are missing. This payment needs the payee's address and email address.") with Add details and Not now; Add opens the payee editor on that section and walks through the remaining gaps after each save. A bug was fixed on the way: a missing email failed the form first, so the prompt never ran on the bank, wallet and card rails. The nudge under the payee names every gap in the error colour with an underlined Add now (tried neutral, changed to red on request); the payment-details panel notice stays neutral.
  • Add Payee modal, entity card. Business shows the address fields inline under Company Name, all required, and the Address chip leaves the optional row; Individual keeps the optional chip and its label reads "Company Name (optional)". Payee ID moved from More info to the Entity card. The entity explanation became a tooltip on an info icon so the card stays one line. Every control renders at the 40px compact height so Email and Phone match; the optional-details chips got their own edge colour so they stay visible against the lighter field border.
  • Add Payee modal, secure link. A real checkbox beside Email and beside Mobile number, both ticked by default, means "send here once this is filled in"; it unticks itself if the value is invalid and sends nothing over an empty field. "Request to add bank account" now starts checked for every payee type. The hint is a brand-tinted note and "Back to manual entry" an outline pill, with tighter spacing.
  • Hand-off files. A standalone HTML sheet of the Add Payee modal in ten states with a light and dark toggle, and a five-page PDF of the Add Customer modal states rendered from it.

Stage 7. A refused Confirm lands on the field

A review of the International rail asked one question: when Confirm Payment Details is refused, does the user always end up on the thing that is wrong? Mostly yes. Required fields were already focused and shaken with a message, missing payee details already got a calm prompt, and a bad payee phone already opened the editor. Four cases did not. With no exchange rate the summary modal still opened, and only after Confirm did a dialog say the payment could not be priced. An unresolved transaction limit repeated the limit card's message in a dialog. The purpose category and the payee's stored email had no field to land on, so the page shook the payee row with no word on why. And with several empty fields the page went to whichever control was declared first in the form, which could sit below another empty field.

All four were closed. No exchange rate now stops Confirm before the modal, with a red line under the recipient block that says what to check. An unresolved limit scrolls to the limit card, which already holds the message and the Edit amount button. The purpose category points at the Purpose field. A stored email that fails the check gets the same calm prompt as a missing one, with Update email opening the editor. And every rail now collects all invalid controls and lands on the top-most one in document order, working down the page one Confirm at a time; this came with the pass's first unit test, since the repo has no test runner wired yet. The card rail's minimum amount was checked and is already caught inline; the two remaining dialogs ("cannot be saved as a draft", "payee temporarily restricted") stay, because there is no field to land on. The rule is recorded in the UI reference as "Blocked submit: where the user lands". A review screenshot then caught the new email prompt firing with no payee selected, a dead end with nothing to update; it now fires only for a selected payee whose stored email has a value that fails, with its own spec, and that case leads the QA matrix.

Who benefits

For users: one calm product in light and dark, fields and buttons large enough to use, text that can be read, status that is never colour alone, a blocked payment that says what is missing and how to fix it, and busy screens stripped of repeated labels.

For the team: a new screen can be built from the reference without a design review for the basics. A colour change is a token edit. The contrast script catches regressions. The audit's open items are a ready-made backlog. The modal state sheets give QA a visual target per state.

Internal FAQ

  • Which palette is final? The navy #004a7c is the main copy. Indigo and calm teal exist as comparison builds for the management decision.
  • Why Inter everywhere? The brand guide specifies it, and one typeface removed a mix of legacy fonts.
  • Why teal on the banner buttons when white text on teal is about 3:1? Chosen on review for brand reasons. It is a deliberate exception and is recorded as such.
  • Why did the field borders get darker in the accessibility stage and lighter again in the polish stage? The original grey measured 1.5:1 and the boundary rule needs 3:1, so the accessibility pass darkened it. On review the darker edge read as heavy, and after four candidates the design owner chose #d1d5db knowing it does not meet 3:1. The contrast script records that exception so it is visible, not hidden. Container borders stayed light throughout.
  • Why are there checkboxes in the send-link form again? The checkboxes removed in the consistency stage only mirrored whether a field was valid and could not be operated. The ones added in the polish stage are real choices, ticked by default, that let a user keep an email on file without sending the link there.
  • What happens when Confirm Payment Details is refused on an international payment? The page takes the user to the field: a required field is focused and shaken with its message; missing or unusable payee details get a calm prompt that opens the editor; no exchange rate or an unresolved transaction limit scrolls to the message inline. The confirmation modal opens only once everything passes.
  • Is any of this in production? No. It is on the design branch and in the three comparison builds. Classic v3 and v3.5 screens were not touched.

Definition of success

The Knowledge phase is done when any designer or developer can read this pack and the UI reference, name the token, size tier or recipe for a given element without asking, explain the seven stages and the rules that came out of them, and list the exceptions and why they exist.

02 | BA

BA

Objective

Agree how we will know the rebrand and consistency pass worked, in measurable terms, before it ships.

Investigation and analysis

Most of the value here is qualitative, so the measures lean on things that can be counted in the codebase and in review, with a small set of user-facing checks after release.

Thinking seed

  • Count of hand-typed hex colours in v4 templates and styles. The baseline before this pass was in the dozens; the target is zero outside documented exceptions.
  • Count of distinct dropdown and button recipes in the v4 app. The audit found several of each; the target is one per component.
  • Contrast script result: every token pair passes, every build, as a gate, with the field border listed as the one accepted exception.
  • Guardrail: no regression in form completion on Send Payment and Add payee after the modal restructure and the missing-details prompt.
  • Guardrail: zero accessibility defects raised against focus visibility, icon-button names or colour-only status.
  • Signal: fewer payments blocked at Confirm for missing payee data, now that the prompt walks the user to the fix.

Working strategy

Record the baseline counts from the audit, keep the contrast script in the pipeline, and schedule one post-release review of the two restructured modals and the Send Payment prompt with support tickets as the signal.

Definition of success

The phase is done when the counts above have a baseline, a target and an owner, the contrast gate is agreed, and the post-release review is on the calendar.

03 | To Do

To Do

Objective

Turn the design-branch work into merge-ready, reviewable pieces.

Investigation and analysis

The branch holds roughly 620 changed files, most of them from the token sweeps and the accessibility pass. They split naturally into: tokens and global styles, shared components, page-level changes, modal restructures, Send Payment behaviour, and documentation.

Thinking seed

  • Which slice can merge first with the lowest risk? Tokens and global style fixes change the look everywhere but touch few files.
  • Which changes alter behaviour rather than style? The Add payee restructure, the send-link defaults (channels and bank request on by default), the Send Payment missing-details prompt and gate order, and the Verification Center severity model are the ones to review as features, with tests.
  • What is the Definition of Done for a style change: contrast script green, lint clean, screens clicked through in light and dark.

Working strategy

Open one pull request per slice, in the order tokens, global styles, shared components, pages, modals, Send Payment behaviour, docs. Link the change log section for each. Flag the behavioural changes for QA.

Definition of success

The phase is done when the branch is split into reviewable pull requests with acceptance criteria, the behavioural changes are flagged, and the Definition of Done is agreed.

Component states

  • Fields: 44px by default, 40px compact inside modals and under Send Payment's Additional details, 32px in table cells; field border, brand border plus ring on focus, red border and a shaking message on error after the field is touched, 50% opacity when disabled, red asterisk for required, "(optional)" in the label otherwise.

  • Choice rows: 28px icon tile that fills navy when selected, 13px bold name with the masked number beside it ("•••• 1234"), page-tint hover, brand-tint selection, 3px gap between rows, dashed green "Add new" tile at the top.
  • Modals: 20px shell, one surface for header, body and footer, title 20px semibold with a 12px subtitle, close icon top right, Cancel outline then primary at 120px each.
  • Blocked submit: the page opens the collapsed panel if the problem is inside it, scrolls to the top-most invalid field, focuses it, shakes it and shows its message; controls with no field of their own point at the field that drives them. A centred info dialog is used only where there is no field (payee record gaps), and it names every gap with one action that leads to the fix and a Not now. Never a silent refusal, a shake alone, or a dialog with no way to the field.
  • Empty: one white card with a 60px icon circle, 18px title, one helper line and one compact primary action. Never a fake list skeleton.
  • Loading: shimmer skeletons for tables and panels, a spinning icon inline, a full-screen blurred overlay only for whole-page waits.
  • Feedback: centred alert dialogs for success, failure, info and warning; inline banners on the success, warning and error surfaces; no toasts.

Simplicity patterns from this pass

  • Required fields in one card. A clear, separate choice (Individual or Business) with pill buttons, explained in a tooltip rather than a subtitle. The choice moves fields: a business's address sits inside the card, an individual's behind an optional chip.
  • Optional sections as a single row of dashed chips, opened one at a time, with a tick once completed and a red "Required" tag when a choice makes them mandatory.
  • Controls that only mirror derived state are removed and replaced with a status line. Where a real choice exists, it is a labelled checkbox beside the field, on by default, as with the send-link channels.
  • Heights follow importance: the primary choices on a page are 44px, supporting details 40px.
  • A blocked action explains itself and offers the fix in one click.

Definition of success

The phase is done when every v4 element can be traced to a token and a recipe in the UI reference, dark mode is reviewed on every changed screen, and the deliberate exceptions are listed with their contrast figures.

05 | Compliance Sign-off

Compliance Sign-off

Objective

Confirm the pass changes nothing about what data is collected or shown, and that accessibility obligations are met.

Investigation and analysis

The restructured Add payee modal moves fields around but collects the same data. The send-link form now has real per-channel checkboxes, ticked by default, and the "request bank account" option starts checked for every payee type, so a secure link asks for bank details unless the user unticks it. The Send Payment prompt asks for data the payment already required; it only surfaces the gap earlier and in words. No new personal data is captured and no masking was weakened: account numbers are still shown as the last four digits only, and the Verification Center lists the documents each compliance case needs up front.

Thinking seed

  • Does the four-dot mask beside the name reveal anything the previous format did not? It shows the same last four digits.
  • Does the Individual or Business choice change which fields are required in a way Legal needs to know? It makes company name and address required for a business, as before; the address now sits inside the card.
  • Is "request bank account" on by default acceptable for every payee type, or should any type start unticked?
  • Is the field-border exception acceptable to cite in an accessibility audit alongside the figures?

Working strategy

Walk Compliance through the two restructured forms and the Send Payment prompt with before-and-after screenshots and the modal state sheets, confirm no change to data capture, consent or masking, note the new defaults, and attach the contrast report with its one exception.

Definition of success

07 | QA Scheduled

QA Scheduled

Objective

Prove that every Send Payment journey still works end to end after the pass, in both themes. The main criterion is simple: nothing breaks. No modal dead-ends, no refused Confirm without a way to the field, no journey that worked before and does not now. The fixes change behaviour only where a journey was broken; the look of the page does not change anywhere else, and any visual difference found is a defect.

Investigation and analysis

The pass touched the shared submit path, so every rail is in scope, not only International. The behavioural changes are the Add payee modal (entity choice, inline business address, optional chips, send-link channels and bank request on by default), the Send Payment missing-details prompts, the screen-order landing on every rail, the International no-rate and limit handling, the Verification Center severity model, and the Instant Demo modal (primary action depends on expert availability). The modal state sheets in the design-system folder are the visual targets for the Add payee and Add customer modals; the UI reference section "Blocked submit: where the user lands" is the behavioural target for Send Payment.

One break was found in review during the pass and fixed before hand-off: with no payee selected, Confirm on the International rail opened the "Payee email address needs attention" prompt, and its Update email button had no payee to open, a dead end. The prompt now fires only for a selected payee whose stored email has a value that fails; with no payee, Confirm lands on the payee field. QA re-checks that exact case first.

Thinking seed

The Send Payment matrix. Run every row on every rail: bank account (ACH, same-day ACH, wire, RTP, check by mail, print and email, let the payee choose), card, and wallet (ACH, wire, check, international, virtual card).

  • Empty form, Confirm: lands on the amount, no dialog. Only the payee missing: lands on the payee field, no prompt. Two or more empty fields: the top-most is focused first, the next Confirm moves down.
  • Payee selected with a gap (email, address, company; several at once): the calm prompt names every gap; Add opens the editor on the right section; after save the form re-reads and asks for the next gap; Not now returns to the payee field. Payee with a malformed stored email: the "needs attention" prompt; Update email opens the editor on the email page. Payee with an invalid phone (international): the alert with Update opens the phone page.
  • Additional details collapsed with an error inside: the panel opens and the field is focused. Wallet balance short: the wallet field. Bank account not verified: the verification modal, and Confirm resumes after it.
  • International: Confirm with no exchange rate (inline message, no modal), while the rate is loading (inline "still getting" message), with a hard limit shown (scrolls to the limit card), after a soft-limit Proceed and after a soft-limit Cancel (Edit amount opens), amount under $10, no destination currency, no recipient bank.
  • Every modal the page opens: Confirm Payment Details, the payee editor on each page, add bank account, bank verification, add international bank, check details, recurring, notify payee, attachments, comments, remittance, transaction history, compliance freeze, OTP and 3DS. Each must open, do its job, close, and hand control back to the form. A primary button that does nothing is a blocker.
  • Save as well as Confirm, and edit or clone of an existing payment, on each rail.
  • Theme and keyboard: every case in light and dark, including the new inline rate message and the softened dark text; a keyboard-only run through the entity pills, info tooltip, optional chips, send-link checkboxes and dropdown rows, with the focus ring visible at every stop and every icon-only button announcing a name.
  • No visual drift: compare each screen with the reference screenshots and the state sheets; spacing, radius, height, hover and selection must match outside the four fixes.

Working strategy

Write one case per cell of the matrix, pair each with the expected landing or screenshot, run on the main build and on one comparison build, and assign a tester and a date. Log any dead-end modal or alert-with-no-way-to-the-field as a blocker, not a cosmetic defect.

Definition of success

The phase is done when every rail has its matrix written with expected landings, the dead-end case found in review is on the list, the keyboard and theme runs are scheduled, and the "nothing breaks, no visual change outside the fixes" criterion is agreed as the exit bar.

08 | In QA

In QA

Objective

Investigation and analysis

Two kinds of defect. A break: a modal whose button does nothing, a prompt that appears when it should not (such as with no payee selected), a refused Confirm that ends in a dialog with no way to the field, a journey that cannot be completed. Working strategy
